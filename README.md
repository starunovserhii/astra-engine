# ASTRA Engine

Собственный расчётный астрологический движок для платформы ASTRA — не обёртка
над сторонним сервисом и не Swiss Ephemeris, а самостоятельная реализация,
собравшая в себе то, что анализ рынка (Part 1 брифа ASTRA) отметил как
сильные стороны конкурентов:

- **скорость Chronos** ("Астропроцессор" — вероятный текущий инструмент
  Оксаны Пламеновой, для которой строится ASTRA) — заявленные ~0.5с на
  карту мы обгоняем на два порядка (см. «Производительность» ниже);
- **строгость Astro.com/Astrodienst** — движок сверен не только внутренними
  самотестами, но и реальной эталонной картой (Rodden Rating AA) с
  astro.com;
- **гибкость Astro-Seek** по системам домов — поддержаны все 8 запрошенных
  систем через расширяемую (strategy pattern) архитектуру, а не через
  захардкоженный Placidus;
- **честность профессионального ПО**: там, где точность метода ограничена
  (Хирон, Кох на экстремальных широтах), это явно помечается в
  `meta.warnings`, а не выдаётся молча как точный факт — тот же принцип,
  что в §24 брифа ASTRA ("AI Safety / Quality") применён здесь к самим
  вычислениям.

## Архитектура

```
ASTRONOMICAL ENGINE   (astronomical/*)   — эфемериды, время, узлы, Лилит, Хирон
        ↓
ASTROLOGICAL ENGINE   (astrological/*)   — дома, аспекты, достоинства, производные точки
        ↓
CHART ASSEMBLY        (charts/*)         — натал, синастрия, транзиты, прогрессии, соляр, хорар
```

Строгое разделение слоёв — принцип §8 проектного брифа ASTRA: **AI никогда
не считает координаты сам**. Этот пакет не содержит ни строчки
интерпретационной логики — только числа и их источник (`meta.ephemerisSource`,
`meta.warnings`). Интерпретации — задача отдельного AI-слоя поверх этого API.

## Почему astronomy-engine, а не Swiss Ephemeris

Swiss Ephemeris (стандарт де-факто в профессиональном софте) распространяется
под двойной лицензией AGPL/коммерческая. Для закрытого SaaS AGPL — риск
(вынуждает открывать код или платить за коммерческую лицензию с самого
начала, до валидации бизнес-модели). `astronomy-engine` (Don Cross, на
VSOP87/ELP2000) — MIT, без ограничений, точность порядка угловых секунд для
внутренних планет и метода расчёта Луны, чего с большим запасом достаточно
для астрологии (мы валидируем с допуском в угловые минуты — на два порядка
грубее реальной точности библиотеки).

## Системы домов

Поддержаны Placidus, Whole Sign, Equal, Koch, Regiomontanus, Campanus,
Porphyry, Alcabitius — через единый `calculateHouses(system, inputs)` с
strategy-паттерном (`src/astrological/houses.ts`), так что добавление новой
системы не требует переписывать ядро (требование §7 брифа).

Проверка корректности — двухуровневая:

1. **Структурные самотесты** (`src/__tests__/run.ts`, часть 1): для
   произвольной тестовой точки каждая система обязана дать
   `cusp1 == Asc`, `cusp10 == MC` (кроме Whole Sign/Equal — это фича этих
   систем, не баг), `cusp(n) + 180° == cusp(n+6)` и, главное, **строго
   монотонный круговой порядок куспидов** (сумма 12 дуг ровно 360°, без
   wrap-around "по модулю"). Именно последняя проверка в процессе
   разработки поймала реальные баги: у Regiomontanus/Campanus/Koch
   куспиды 5/6/11/12 изначально попадали не в тот квадрант (ветвь решения
   уравнения пересечения большого круга с эклиптикой выбиралась неверно) —
   куспиды формально были симметричны попарно, но не выстраивались в
   правильный круг. Найдено перебором обеих ветвей решения и подтверждено
   граничными условиями (например, для Koch: `ascendant(RAMC − D) == MC`
   ровно, где `D` — полудуга склонения MC).
2. **Эмпирическая валидация** (часть 2): натальная карта Альберта Эйнштейна
   (14 марта 1879, 10:50 UT, Ульм, 48°24'N 10°00'E) — эталон с наивысшим
   рейтингом достоверности (Rodden Rating AA, оригинал свидетельства о
   рождении), источник astro.com/Astrodienst. Солнце, Луна, Асцендент и
   местное звёздное время сходятся с допуском 2–5 угловых минут.

Все 94 проверки в `npm test` проходят.

### Честно про ограничения

- **Хирон** — двухтельная кеплеровская орбита от оскулирующих элементов на
  эпоху 2025-01-01 (не полноценная численная интеграция с учётом возмущений
  от Сатурна/Урана). Точность деградирует по мере удаления даты расчёта от
  эпохи элементов; это явно помечается в `meta.warnings` при использовании
  Хирона в карте. Для продакшена — обновлять элементы не реже раза в год
  либо подключить JPL Horizons API.
- **Koch на околополярных широтах** — как и Placidus/Alcabitius, математически
  неприменим там, где семидуга не определена (циркумполярные случаи);
  движок честно откатывается на Equal houses и помечает `reliable: false`,
  а не подставляет недостоверные куспиды молча.
- **Время рождения неизвестно** — вместо блокировки или тихой подстановки
  полудня движок строит **solar chart** (Солнце в начале 1 дома, куспиды
  недоступны, Vertex/Жребий Фортуны честно опускаются) с явным
  предупреждением в `meta.warnings` — решение из §37 брифа.

## Производительность

Замер (`npm run demo` использует API вживую; для чисел — `npx tsx
src/__tests__/perf.ts`), обычное железо контейнера сборки:

| Операция | Время |
|---|---|
| Полная натальная карта (10 планет + Хирон + узлы + Лилит + Vertex + Жребий + дома + аспекты + достоинства) | ~2 мс |
| Синастрия (2 готовые карты) | ~0.3 мс |
| Транзиты к натальной карте | ~2 мс |

Ориентир из конкурентного анализа — Chronos "Астропроцессор" заявляет
~500 мс на карту. ASTRA Engine быстрее на ~2 порядка, что для сценария
"AI Copilot считает transits в реальном времени во время консультации"
(§12 брифа) существенно: можно пересчитывать карту при каждом изменении
параметров без заметной задержки в интерфейсе.

## API

```ts
import {
  calculateNatalChart, calculateSynastry, calculateTransits,
  calculateSecondaryProgressions, calculateSolarReturn, calculateHoraryChart,
} from 'astra-engine';

const chart = calculateNatalChart(
  { utc: new Date(Date.UTC(1990, 5, 15, 8, 30, 0)), timeKnown: true },
  { latitude: 55.751244, longitude: 37.618423 },
  { houseSystem: 'placidus' },
);
```

Полный публичный API — `src/index.ts`. Живой пример со всеми типами карт —
`npm run demo`.

## Скрипты

- `npm run build` — компиляция в `dist/`
- `npm test` — структурные + эмпирические проверки (94 проверки)
- `npm run demo` — демонстрация всех типов карт на примере
